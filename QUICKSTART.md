# QUICKSTART — Jev Customer Service\n\nEste eval usa o Jev 1.13 através do OpenRouter Decisions API para classificar mensagens de clientes contra as categorias existentes em `./dados.json`.\n\nO primeiro experimento é deliberadamente simples: o código lê somente os nomes de `dados.json` e monta:\n\n```json\n{\n  "categories": {\n    "agendamento": ["advogados", "corretores-de-imoveis"],\n    "ecommerce": ["comercios", "cargas-e-encomendas", "construcao-civil"]\n  }\n}\n```\n\nOs totais, telefones e demais métricas de `dados.json` não são enviados ao Jev.\n\n## 1. Configuração\n\nCrie `.env` a partir de `.env.example`:\n\n```bash\ncp .env.example .env\n```\n\nConfigure:\n\n```env\nOPENROUTER_API_KEY=sk-or-...\nOPENROUTER_JEV_MODEL=typesafe/jev-1.13\n```\n\nO Jev usa a Decisions API do OpenRouter, e não `/api/v1/chat/completions`:\n\n```\nPOST https://openrouter.ai/api/alpha/decisions\n```\n\n## 2. Dados\n\nColoque o arquivo `./dados.json` no diretório raiz.\n\nA estrutura esperada contém:\n\n```json\n{\n  "categorias": {\n    "agendamento": [{ "categoria": "advogados", "total": 44 }],\n    "ecommerce": [{ "categoria": "comercios", "total": 58 }]\n  }\n}\n```\n\nO script extrai somente `categoria`.\n\n## 3. Executar\n\n```bash\nnpm run jev:customer-service\n```\n\nO eval executa várias mensagens de teste cobrindo serviço profissional/agendamento, entrega e encomenda, taxi/viagem, compra de produto, preço, orçamento, disponibilidade, compra imediata, cancelamento, status de pedido, urgência e reclamação.\n\nPara cada caso o Jev retorna uma distribuição da escolha:\n\n```json\n{\n  "choice": "cargas-e-encomendas",\n  "confidence": 0.91,\n  "probabilities": {\n    "cargas-e-encomendas": 0.91\n  }\n}\n```\n\nOs valores acima são apenas o formato esperado; os resultados reais vêm da execução.\n\n## 4. O que estamos testando\n\nA pergunta atual é uma única `choice`: qual categoria de negócio representa melhor a necessidade principal do cliente?\n\nAs instruções cobrem identificação semântica além de matching literal: sinônimos, linguagem coloquial, abreviações, erros de digitação, intenção implícita, entidades, verbos, objeto da solicitação, origem/destino, finalidade, múltiplas intenções e contexto.\n\nNesta primeira versão não existe uma categoria artificial `other`/`none`. Portanto, o Jev é obrigado a escolher uma das categorias existentes. Isso é intencional para medir primeiro a capacidade do catálogo atual de representar as mensagens.\n\n## 5. Próxima evolução do eval\n\nDepois de validar a taxonomia de categorias, podemos separar a classificação em perguntas atômicas no mesmo request:\n\n- `channel_intent`: comprar, agendar, entregar, viajar, consultar preço, consultar disponibilidade, acompanhar, cancelar etc.;\n- `transport_intent`: taxi/viagem versus entrega/encomenda;\n- `commerce_intent`: descobrir produto, preço, estoque, comprar, cancelar ou acompanhar pedido;\n- `service_intent`: encontrar profissional, agendar, remarcar ou cancelar;\n- `urgency`: sem prazo, prazo desejado, prazo explícito ou bloqueio imediato;\n- `has_origin`;\n- `has_destination`;\n- `has_product`;\n- `has_quantity`;\n- `has_schedule`;\n- `has_price_question`;\n- `needs_human_review`.\n\nA ideia é não transformar uma pergunta ampla em um único rótulo quando o sistema precisar de vários sinais independentes. O Jev retorna uma distribuição por pergunta, permitindo preservar a incerteza para a camada de decisão.\n\n## 6. Observação sobre as categorias\n\nO catálogo atual é a fonte de verdade do espaço de classificação. Se uma mensagem de taxi, delivery ou outro domínio não tiver uma categoria correspondente em `dados.json`, o resultado atual continuará sendo uma escolha forçada entre as categorias disponíveis.\n\nQuando a taxonomia estiver validada, vale adicionar explicitamente uma opção `none`/`other` e/ou separar primeiro o domínio (`agendamento` vs. `ecommerce`) e depois a categoria. Isso evita usar uma categoria existente como substituta para uma intenção que não pertence a ela.\n
